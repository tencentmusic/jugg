# 编译流水线

Jugg 的编译流水线不是简单地“编译当前文件”。它会按文件类型拆分任务，把资源产物、生成源码、普通源码和 DEX 产物串起来，并把结果放入 staging，等待部署阶段消费。

## 输入来自哪里

Jugg 会把本轮未编译的文件归类为几种输入：

| 输入类型 | 常见来源 | 后续去向 |
|---|---|---|
| Java / Kotlin | 业务源码、生成源码 | 编译为 class，再进入 DEX / 混淆处理。 |
| Resource | `res/` 下资源文件 | 生成资源 overlay、`R` 相关产物，必要时触发源码编译。 |
| AndroidManifest | Manifest 变化 | 生成需要写回 APK 的更新文件，通常影响部署策略。 |
| Asset | `assets/` 文件 | 作为 overlay 下发。 |
| Native lib | `.so` 文件 | 写入 APK 并重新签名，通常需要安装或重启。 |
| Class | 依赖或已编译 class 输入 | 进入 DEX 或兼容处理。 |

## 阶段如何衔接

一次增量编译通常按下面的逻辑推进：

1. 先处理 assets 和 native lib，生成可部署文件。
2. 再处理资源和 Manifest，生成资源 overlay、`R` 相关产物和可能的绑定源码。
3. 资源阶段产生的源码继续进入源码编译阶段，而不是直接部署。
4. Java/Kotlin 以及生成源码被编译为 class。
5. class 再进入 DEX、release 混淆或补偿处理。
6. 所有成功产物写入 staging，等待部署数据规划。

这就是为什么一次资源修改有时会看到源码编译：资源阶段可能改变 `R`、ViewBinding 或 DataBinding 相关代码，后续必须继续编译才能得到可部署产物。

## 成功文件与失败文件如何处理

Jugg 会按文件记录编译结果：

- 成功文件会从“待编译”状态移走。
- 失败文件会保留在待处理状态，方便下一次运行继续处理。
- 编译产物只进入 staging，不会立刻成为已部署历史。
- 如果用户取消编译，首轮状态会回滚，避免下一轮误以为文件已经处理过。

这种设计保证了“编译成功”和“部署成功”之间不会混淆。

## 为什么会继续编译第二轮

第一轮编译成功后，Jugg 会基于部署数据和历史索引做影响分析。命中以下情况时，会继续补编译：

- 修改了类结构、方法签名、字段或继承关系。
- 修改了会影响调用方的常量。
- 修改了接口、抽象方法或泛型约束。
- release/minify 场景需要补偿已内联或已移除的成员。

这类补编译属于正常流程。它的目的不是“把所有源码重编一遍”，而是只补齐会受到本轮变化影响的那部分代码。

## 与 Gradle 的区别

| 对比项 | Jugg 编译流水线 | Gradle 构建 |
|---|---|---|
| 输入范围 | 本轮变化和受影响文件 | 完整任务图和构建脚本定义 |
| 输出目标 | 部署所需的增量产物 | 完整 APK/AAB、测试 APK、构建缓存 |
| 依赖构建脚本 | 依赖已有快照，变化时可能回退 | 权威来源 |
| 适合场景 | 小范围迭代、快速部署 | 建立基线、复杂插件、依赖和变体变化 |
