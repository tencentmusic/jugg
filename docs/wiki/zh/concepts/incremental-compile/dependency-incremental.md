# 依赖库增量编译

构建文件变化通常会让 Jugg 回到 Gradle。Gradle 配置可以影响 task、source set、variant、依赖解析、代码生成和插件行为，Jugg 不能只凭文件变化自动判断本轮是否只有依赖库改动。

依赖库升级是一个受控例外。Jugg 会先让用户确认 build 文件 diff，再通过 Gradle 读取依赖变化。只有用户再次确认变化结果后，变化库才会进入增量编译和部署判断。

## 为什么需要确认

Jugg 不穷举 Gradle 构建信息的所有变化。这样做维护成本高，也不能保证每个工程的自定义配置都被覆盖。漏掉 build 文件中的非依赖变化，可能导致本轮编译基于错误上下文运行。

因此，依赖库增量编译把判断分成两步：

```text
检测到 build 文件变化
  -> 展示 build 文件 diff
  -> 用户选择查找变化依赖或回退 Gradle
  -> 通过 Gradle 读取当前依赖信息
  -> 与上次基线依赖信息对比
  -> 展示变化库结果
  -> 用户确认后进入增量编译
```

非回退操作带有倒计时确认，用于降低误点风险。用户也可以直接选择 Gradle 回退，重新生成完整构建基线。

## 依赖变化从哪里来

依赖 diff 依赖两份数据：

| 数据 | 生成时机 | 用途 |
|---|---|---|
| 基线依赖库信息 | Gradle 构建完成时保存 | 作为后续 diff 的旧版本 |
| 当前依赖库信息 | 用户选择查找变化依赖时重新读取 | 与基线对比，得到新增、升级、降级或删除的库 |

早期方案曾尝试用 IDE sync 结果判断依赖变化。IDE sync 和 Gradle 编译是独立异步流程，难以保证与本轮编译一一对应；后续改为通过 Gradle 读取。远端 Gradle 场景下，diff 也可以在远端执行，减少本地读取和传输成本。

## 变化库如何进入编译

依赖库内容主要包括 jar、资源文件和 assets。这些输入和 Jugg 已有的源码、资源、assets 编译链相同，因此变化库可以复用内置编译流程。

直接编译整个变化库会拉长耗时。Jugg 会先比较升级前后的库文件，只把变化文件送入编译：

```text
变化 library
  -> 与基线 library 做文件 diff
  -> jar 变化进入源码 / dex 编译
  -> res 变化进入资源编译
  -> assets 变化进入 asset overlay
  -> 产物交给部署阶段
```

已有测试数据中，直接编译一个约 20 MB 的协议库约需 2 分钟；做库内文件 diff 后，依赖库编译耗时约 5 秒。查找依赖变化本身仍需要执行 Gradle，整体流程主要耗时在这个阶段，常见范围为 40-80 秒。

## 部署侧处理

依赖库增量编译不只处理升级。Jugg 还要区分新增、删除、降级和代码回退：

| 场景 | 处理方式 |
|---|---|
| 正常升级且文件有变化 | 编译变化文件并部署增量产物 |
| 新增依赖库 | 新库文件进入本轮增量编译和部署判断 |
| 删除依赖库 | 作为 removed library 进入部署数据判断 |
| 升级后又回退版本 | 移除对应增量部署，避免设备侧保留错误产物 |
| 再次升级但内容回退 | 同样需要移除已不应存在的增量部署 |

这些分支的目的，是让设备侧状态和当前依赖库内容一致，而不是只把新文件推上去。

## 什么时候不适合

以下情况更适合 Gradle 回退：

- build 文件里除了依赖库，还修改了会影响 APK 的配置。
- 修改了 Gradle 插件、source set、variant、annotation processor 或 Kotlin compiler plugin 配置。
- 依赖变化后出现源码解析失败，且更新 compile context 后仍无法恢复。
- 用户无法确认展示的依赖变化是否符合预期。

如果用户确认 build 文件变化对当前开发没有影响，也可以选择忽略。忽略后，Jugg 会恢复增量状态，并把本次 build 文件变化当作未发生处理；后续仍可手动回退 Gradle 重建基线。
