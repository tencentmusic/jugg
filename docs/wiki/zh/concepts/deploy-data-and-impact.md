# 部署数据与影响分析

Jugg 编译出增量产物后，需要判断这些产物能否在线热重载，还是需要热修复或重新安装。同时，部分 class 变化还会影响未直接修改的源码，需要继续编译。

## 部署数据解决什么问题

原文中的部署策略是热重载优先、热修复兜底。判断依据是新旧 class 结构差异：

| 情况 | 处理倾向 |
|---|---|
| 方法体变化，类结构不变 | 热重载 |
| 新增类 | 作为新类下发，必要时重启后生效 |
| 删除方法或修改方法签名 | 热修复或更保守路径 |
| 修改字段或类结构 | 热修复或更保守路径 |
| 资源变化 | 下发资源增量产物 |
| Manifest 或 native lib 变化 | 写回 APK、对齐、重签名并安装 |

Jugg 会解析 APK 中的类结构，并与本轮编译产物比较，决定部署方式。

## 影响分析

只部署被修改 class 可能遗漏调用方。例如删除一个方法后，被修改类可以编译成功，但旧调用方如果没有重新编译，运行时可能出现 `NoSuchMethodError`。

Jugg 使用 APK 解析数据库查询类之间的调用关系和继承关系：

```text
变化 class
  -> 对比新旧方法、字段和抽象方法
  -> 查询引用类、子类和源码路径
  -> 找到受影响源码
  -> 加入下一轮编译
```

原文中列出的扩散编译场景包括：

- 方法签名变化或删除时，编译引用类源码。
- 字段签名变化或删除时，编译引用类源码。
- 抽象父类新增抽象方法时，编译子类源码。

虚函数调用需要把子类引用也纳入查询范围。增量部署过的类，则需要使用部署后的类结构分析。

## 与资源和 APK 更新的关系

资源变化会通过 aapt2 `inclink` 生成资源增量产物和 `resources.arsc`。如果资源 ID 有新增，还可能生成 `R.java` 并触发源码编译。

Manifest 和 native lib 不属于普通资源 overlay。Manifest 需要写回 APK，再执行对齐、重签名和安装；native lib 更新也可能触发 APK 更新或更保守部署。
