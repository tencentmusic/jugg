# Wiki 能力篇写作准则

> 最后核对：2026-06-15
> 一致性规则：文档与代码冲突时，以代码为准。

---

## 1. 文档定位

本页面向维护 `docs/wiki/**/capabilities/` 的 AI 和开发者，回答：

- 能力篇如何表达“支持什么、不支持什么、需要什么前置条件”。
- 能力篇如何解释生效机制，同时避免写成源码说明或排查手册。
- 编译、部署、测试、工具等能力跨领域时，页面入口和真实机制如何同时讲清。
- 写具体能力事实前必须读取哪些依据，避免只靠写作规范编内容。
- 如何避免把稳定能力写成风险清单。

通用 Markdown、frontmatter、提示块、链接和中英文同步规则见 `10_wiki_authoring.md`。Wiki 工程运行和构建见 `10_wiki_architecture.md`。

---

## 2. 协作宗旨

能力篇面向用户回答两个问题：

1. Jugg 当前支持哪些操作或修改，哪些不支持，哪些需要先完成前置动作。
2. 这项能力如何生效，机制要精炼到足以理解边界，不展开成实现文档。

能力篇不是 troubleshooting，也不是源码索引。读完后，用户应该能判断“我的场景是否被支持”和“它大致通过哪条机制生效”。

---

## 3. 页面入口按用户视角命名

能力页优先按“用户想完成什么 / 改了什么 / 要验证什么”建立入口，而不是按内部实现层命名。

推荐判断方式：

- 用户会从操作目标搜索，例如 `Clean Reinstall`、`Code Swap`、`Android Test`、`MCP`、`so 更新`。
- 用户会从修改对象搜索，例如 `Manifest`、`资源编译`、`常量引用分析`。
- 用户不会优先搜索内部协作者、transport 名称、缓存结构、action 类名或 task 名称。

页面入口可以按用户最容易找到的位置放置；正文必须说明真实执行阶段和关联能力。

---

## 4. 能力信息架构分层

能力篇的目录入口、支持表和机制说明应分层，避免把过宽能力、共享机制和内部实现混在同一页面。

通用规则：

- 页面入口按互斥的用户修改对象或操作目标组织。若一个标题会自然覆盖多个兄弟页面，说明标题太宽，应拆成更具体的能力入口。
- 跨多个能力复用的机制独立成页。具体能力页只说明“本能力会触发该机制”，再链接到机制页，不重复承载机制全文。
- 支持范围先列用户可识别的最小对象，再在机制部分解释内部实现。表格第一列优先写用户在代码、配置或界面中能看到的对象，不优先写内部组件名。

判断方式：

- 同一用户改动应只有一个主入口；如果可同时归到多个同级页面，需要重新划分页面边界。
- 一段机制如果同时解释多个页面为什么生效，就不应塞进单个能力页。
- 如果用户无法从项目文件中直接识别表格第一列，说明该列过于实现化，应换成更贴近用户的对象。

## 5. 事实来源前置要求

`10_wiki_authoring.md` 和本文只规定写作标准，不承载具体能力的全部事实。编写或修改任何能力篇前，必须先读取足够的专题文档和必要实现代码，再下笔。

硬性要求：

- 先按 `99_index.md` 任务路由找到对应专题文档，例如编译读 `02_*`，部署读 `03_*`，测试读 `06_*`，MCP/CLI 读 `08_*`。
- 如果能力跨领域，必须同时读取相关领域文档。例如 Manifest / `.so` 同时涉及编译产物和 APK 更新重签名，不能只读资源编译文档。
- 当页面要写“支持 / 不支持 / 生效方式 / 前置条件”时，必须用专题文档或实现代码支撑；文档没有承载的事实要检查对应实现文件。
- 不允许只读 `10_wiki_authoring.md`、本文和目标 Wiki 页面就开始编写能力事实。
- 完成任务时，执行清单的“依据定位”必须列出实际使用的专题文档或代码文件，而不只列写作规范。

写作规范解决“怎么表达”，专题文档和代码解决“事实是什么”。两者缺一不可。

## 6. 页面结构决策

能力篇优先使用自然、用户可理解的标题。动笔前先判断页面主要回答的问题，再选择章节结构；不要先套固定模板。

页面类型判断：

| 页面类型 | 用户主要问题 | 推荐标题方向 |
|---|---|---|
| 操作 / 修改对象页 | 这个操作或修改是否支持？ | `运行入口与支持范围`、`修改类型与支持范围`、`操作场景` |
| 机制页 | 这项能力为什么能生效？ | `如何运作`、`如何生效`、`生效链路` |
| 状态 / 缓存页 | 状态如何推进，什么时候会复用或失效？ | `状态如何推进`、`缓存更新规则`、`一致性边界` |
| 恢复 / 重试页 | 哪些信号会触发恢复或重试？ | `会自动恢复或重试的信号`、`恢复流程` |
| 展示 / UI 页 | 用户在哪里看到结果，结果如何组织？ | `展示范围`、`结果如何呈现` |
| 归因 / 解析页 | 输出如何归到对象，边界是什么？ | `归因规则`、`解析边界`、`日志展示与归因范围` |
| 工具页 | 用户输入什么，工具输出什么？ | `输入输出边界`、`可完成的任务` |

`已支持能力` 是可选标题，只适合用户能直接按“修改或操作场景”判断支持范围的页面。如果页面主要说明机制、状态对象、恢复策略、触发条件、结果展示或日志归因，应改用更具体的标题。

不同页面类型可以使用不同结构，例如：

```markdown
## 运行入口与支持范围
## Android Test 如何运行
## 关联能力
```

```markdown
## 适用条件
## 生效链路
## 边界
```

```markdown
## 展示范围
## 结果如何呈现
## 关联能力
```

可根据页面主题替换为更具体标题，例如：

- `资源编译如何运作`
- `Manifest 如何生效`
- `Direct Overlay 适用条件`
- `会自动恢复或重试的信号`
- `Android Test 如何运行`
- `MCP 工具如何调用`

避免使用“使用时需要关注”“了解原理需要关注”这类内部清单式标题。

## 7. 支持范围写法

`已支持能力` 只列用户能直接判断的能力项，避免把低概率失败现象、排查线索、状态对象或内部前置条件铺成大表。

硬性约束：

- 不得为了使用表格而统一命名为 `已支持能力`。
- 如果表格内容描述的是入口、展示、归因、状态推进、恢复条件或触发信号，应使用对应语义标题。
- 标题必须描述这一节真正回答的问题，而不是套能力篇模板。

推荐写法：

- 用表格说明“场景 / 当前支持情况 / 生效方式”。
- `已支持能力` 只放支持项；不支持项或需要前置动作的场景不要混入支持表。
- 对明确不支持或需要前置动作的场景，只保留高价值概括，并优先用短 `TIP` / `NOTE` 承接。
- 前置动作应写成用户可执行的动作，例如“先完成对应 Gradle 构建或 Sync”“先连接目标设备”“先安装 agent skill”。
- 不要把通用机制写成某个能力的缺陷。只有当用户必须因此采取动作时，才用短 `TIP` / `NOTE` 说明。

不同能力的表格字段可以按语义调整：

| 能力类型 | 推荐字段 |
|---|---|
| 编译能力 | 修改类型 / 当前支持情况 / 生效方式 |
| 部署能力 | 操作场景 / 当前支持情况 / 部署策略 |
| 测试能力 | 运行入口 / 当前支持情况 / 结果呈现 |
| 工具能力 | 用户任务 / 当前支持情况 / 输入输出边界 |

标题反例：

| 页面 | 不推荐 | 推荐 |
|---|---|---|
| Logcat 归因 | `已支持能力` | `日志展示与归因范围` |
| Test Results UI | `已支持能力` | `结果展示范围` |
| Application Android Test | `已支持能力` | `运行入口与支持范围` |
| Recover 与 Retry | `已支持能力` | `会自动恢复或重试的信号` |

## 8. 生效机制写法

机制部分要解释能力为什么成立，但不能把页面写成实现文档：

- 只保留关键链路、关键产物和跨阶段交接。
- 说明用户可感知的生效方式，例如 overlay、code swap、full swap、APK 更新与重签名、instrumentation、MCP action 调用。
- 如果某能力已有独立页面，当前页面只做简短介绍并链接过去，不重复展开。
- 如果机制依赖多个阶段，明确每个阶段的职责，不要用目录位置改变能力语义。

机制说明应服务于用户判断边界。例如：

- 编译能力说明“产物如何生成，以及是否继续进入源码/部署阶段”。
- 部署能力说明“是否重启、是否 reinstall、是否依赖 JVMTI 或设备状态”。
- 测试能力说明“如何选择 target、如何运行、结果在哪里呈现”。
- 工具能力说明“用户给什么输入、工具做什么、输出能用于什么”。

## 9. 跨领域能力归属

能力篇可以按用户入口归类，但正文必须讲清真实机制。不要把不同语义混成一个模糊能力。

通用规则：

- 页面入口优先服务用户查找；机制描述必须服务事实准确。
- 如果能力跨编译、部署、运行时、测试或工具链，正文要说明主入口、实际执行阶段和关联页面。
- 不要为了目录分类牺牲语义准确性。
- 不要把一个能力的前置产物、执行机制和部署方式混成同一个“编译”或“部署”概念。

示例：

- `.so` 更新页应正面定义用户可获得的能力：Jugg 支持更新已产出的 native lib / `.so` 文件，并通过写入 APK、重新签名后安装生效。C/C++ 源码、CMake、NDK、ABI 或 packaging 变化属于前置条件，用短提示说明“先由 Gradle/NDK 产出新的 `.so`”即可。
- Manifest 页面可作为用户从 Manifest 修改进入的能力入口；正文必须说明它可以参与资源 link，但最终通过更新 APK 并重签名生效。
- Deploy `Code Swap` 页面应按用户感知的热更新能力说明支持范围，不应只描述内部 transport。
- Test `Android Test` 页面应说明支持的运行入口、target 选择和结果展示，不应只展开 `am instrument` 命令。
- Tools `MCP` 页面应说明用户能完成哪些任务和输入输出边界，不应只列 action/schema。

## 10. 语气与取舍

能力篇要减少让用户误解为“不可靠”的表达：

- 开篇应正面定义用户可获得的能力，不要先解释“这不是什么”。
- 不要解释页面为什么放在某个目录；这是维护者视角，不是用户关心的信息。
- 不要把内部讨论或文档迭代中的误判纠偏写成用户提醒。
- 避免大段“可能失败 / 建议回退 / 不属于输入”的列表。
- 避免把通用机制重复包装成每个能力的限制。
- 避免“常见现象”这类低价值章节；除非它能直接帮助用户判断能力是否支持。
- 风险或前置动作优先用短 `TIP` / `NOTE` 承接；真正会破坏状态或需要停止操作时才使用 `WARNING` / `CAUTION`。
